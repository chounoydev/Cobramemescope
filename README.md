# Cobra MemeScope

A memecoin risk scanner built with Vue 3, Vite, and Express. It combines third-party contract-security signals with live DEX market observations and a cross-chain feed of recent token profiles. The browser keeps watchlists locally.

## Requirements

- Node.js 20 or newer
- A PostgreSQL database (Neon or Supabase)
- A CoinGecko demo API key is optional for modest local usage
- A Gemini API key is optional for the Cobra Guide AI assistant

## Start the API

```powershell
cd backend
npm install
Copy-Item .env.example .env
```

Create or select a PostgreSQL database. For Neon, open the project's **Connect** dialog and copy the pooled connection URI. For Supabase, use the **Session pooler** URI for a long-running Node backend. Put the URI in `backend/.env` as `DATABASE_URL`; Neon TLS is enabled automatically, and `DATABASE_SSL=true` can enable TLS for any provider. URL-encode special characters in the database password before placing it in the URI. Set a random `JWT_SECRET` of at least 32 characters as well. Keep the database password private; never put it in frontend environment files, commit it, or send it in chat.

To enable wallet-held meme-token detection, create a GoldRush API key and set `GOLDRUSH_API_KEY` in `backend/.env`. This key is used only by the backend. Email-account users can link an owner-controlled wallet by signing a verification message; no transaction or token approval is requested. The holdings panel checks Solana and supported EVM networks (Ethereum, Base, BNB Chain, Polygon, Arbitrum, Avalanche, and Optimism), displays estimated value and DEX-reported 24-hour market movement, and refreshes once per minute while the account dialog is open. Tokens without a discovered DEX market are omitted, and the panel explains when no priced meme-token balances are found. Price movement is not personal profit/loss.

To enable **Cobra Guide**, create a Gemini API key in [Google AI Studio](https://aistudio.google.com/apikey) and set `GEMINI_API_KEY` in `backend/.env`. Keep this key on the backend; never add it to frontend environment files or source control. The guide is prompted with product guidance for the public website, including scanning tokens, understanding market data, using the watchlist, and account settings; it can also explain the latest scan shown in the app. This is prompt-based guidance, not custom model training. Chat requests use Gemini's stateless mode and are not stored through the Interactions API. The default model is `gemini-3.5-flash-lite` for responsive help; `GEMINI_MODEL` can be changed in `backend/.env` if needed.

```powershell
npm run migrate
npm run dev
```

The API runs on `http://localhost:3001`. `GET /api/health` checks both the API and its database connection; it returns HTTP 503 if PostgreSQL is unavailable. Endpoints include `GET /api/market`, `GET /api/market/trending`, `POST /api/scan`, `POST /api/assistant` (Gemini AI guide), `POST /api/auth/register`, `POST /api/auth/login`, wallet challenge and verification endpoints under `/api/auth/wallet` and `/api/auth/profile/tracked-wallet`, authenticated `GET /api/wallet/holdings`, `GET /api/wallet/balance`, `GET /api/wallet/solana/blockhash`, owner-only `GET /api/admin/donors`, and authenticated watchlist endpoints under `/api/watchlist`.

## Start the frontend

In a second terminal:

```powershell
cd frontend
npm install
Copy-Item .env.example .env
npm run dev
```

Open the Vite URL shown in the terminal (usually `http://localhost:5173`). If the API is unavailable, the market tape falls back to clearly labelled illustrative sample data; contract scans require the API.

## Deploy on Render

The root `render.yaml` defines a free Render web service that builds the Vue frontend and serves it from the Express API on the same HTTPS origin. Before deploying:

1. Create or select a PostgreSQL database and apply the schema by running `npm run migrate` locally with its connection URI in `backend/.env`, or execute `backend/schema.sql` in the provider's SQL editor.
2. Create a Blueprint from this repository in Render. Set `DATABASE_URL` to the database's pooled connection URI and `DATABASE_SSL` to `true` in the service environment. For Neon, copy the pooled URI from the Neon **Connect** dialog. Set `GOLDRUSH_API_KEY` if you want wallet holdings detection. Set a strong `JWT_SECRET` as well. Do not put credentials into `render.yaml`, source control, or frontend variables.
3. Deploy and confirm the service's `/api/health` endpoint returns `{"status":"ok","database":"connected"}`.

The `JWT_SECRET` is generated by Render. Render's free web service can sleep between requests. No paid Render resources are created by this repository configuration.

## Deploy both services on Vercel

The root `vercel.json` deploys the frontend and API as Vercel Services on one domain. The frontend is public at `/`; `/api/*` is routed to the Express backend. The browser uses same-origin `/api` requests both in production and local development, so no `VITE_API_URL` is needed for this setup. Vite development always uses its `/api` proxy; `VITE_API_URL` is only used for production builds such as the separate Render-backend setup.

1. Import the GitHub repository into Vercel and deploy it as a multi-service project using the root `vercel.json`. Keep the service names `frontend` and `backend`.
2. Add these Vercel environment variables to the `backend` service for the Production environment: `DATABASE_URL` (pooled PostgreSQL URL), `JWT_SECRET` (random string of at least 32 characters), and `CRON_SECRET` (a separate random secret). Enable Vercel system environment variables so the backend can allow the exact production and preview deployment origins for wallet sign-in. Redeploy after changing settings. Add optional backend keys such as `GOLDRUSH_API_KEY` and `GEMINI_API_KEY` if those features are needed. Do not prefix backend secrets with `VITE_`.
3. Apply `backend/schema.sql` to the database before using the app, or run the backend migration against that database. Vercel does not run the backend's local/Render startup migration command.
4. Set frontend build variables such as `VITE_PUBLIC_APP_URL` in Vercel if needed. Leave `VITE_API_URL` unset for same-origin API routing.
5. Deploy and verify `/api/health` reports `"status":"ok"`, `"database":"connected"`, `"schema":"ready"`, and `"authentication":"ready"`. This endpoint performs a read-only database/schema check. Login returns a configuration error if `JWT_SECRET` is missing; public market/chart endpoints remain available without it. The backend function allows up to 60 seconds for external market/chart providers. The Vercel cron invokes `/api/cron/account-deletions` on the `0 0 * * *` schedule (midnight UTC); the endpoint accepts only Vercel's scheduled-cron request with the configured schedule and `Authorization: Bearer <CRON_SECRET>` header. Do not manually call this endpoint because it permanently deletes accounts whose grace period has expired. On Hobby, scheduled runs are daily with up to 59 minutes of timing variance, so an account deletion may be processed about 25 hours after its grace period ends.

For local development with separate Vite and Express processes, use the existing two-terminal steps above. Vite proxies `/api` to `http://localhost:3001`, matching the same public path used by the Vercel rewrite. To exercise Vercel's multi-service rewrites locally, use `vercel dev` from the repository root.

## Deploy the frontend on Vercel with a Render API

Vercel hosts the Vue frontend; the Express API and PostgreSQL database must remain on a backend host such as Render. Deploy the backend first by following the Render steps above. In the Vercel project, import this repository and set **Root Directory** to `frontend`. The `frontend/vercel.json` file configures the Vite build, `dist` output, and SPA fallback for direct visits such as `/admin`.

Set these Vercel **Production** environment variables before deploying:

- `VITE_API_URL`: the public HTTPS URL of the deployed backend, with no trailing slash (for example, `https://your-api.example.com`).
- `VITE_PUBLIC_APP_URL`: the public HTTPS URL of the Vercel frontend. Set this when using Phantom mobile deep links.

In the Render backend service, set `FRONTEND_ORIGIN` to the exact Vercel production origin, including `https://` and without a trailing slash (for example, `https://your-app.vercel.app`). Add any custom production domain as a comma-separated origin. On Vercel, the backend allows the exact `VERCEL_URL`, `VERCEL_BRANCH_URL`, and `VERCEL_PROJECT_PRODUCTION_URL` hosts when Vercel system environment variables are enabled; add custom frontend domains to `FRONTEND_ORIGIN` as well.

The frontend does not contain backend credentials. Set `DATABASE_URL`, `JWT_SECRET`, and optional provider keys only in the Render backend environment. Apply `backend/schema.sql` to the database before using database-backed features, and verify `https://your-api.example.com/api/health` reports a connected database before testing the Vercel site.

## Prepare the Android APK

The Android app uses Capacitor to package the frontend as an online-connected Android WebView. Deploy the Render service first; APK builds require its public HTTPS URL for API requests.

1. Copy `frontend/android.env.example` to `frontend/.env.android` and replace the example URL with the deployed Render URL. This file contains a public URL, not secrets; never put private API keys in frontend environment files.
2. Install Android Studio with the Android SDK and JDK 21.
3. In `frontend`, run `npx cap add android` once, then `npm run android:build`. The debug APK is produced at `frontend/android/app/build/outputs/apk/debug/app-debug.apk`.
4. Test the APK on a real device. The wrapper requires internet access. Phantom wallet sign-in through a browser extension is not available in the Android WebView; native Phantom mobile-wallet deep-link support would need separate implementation before that flow can be relied on in the APK.

The debug APK can be sideloaded for testing, but is not a Play Store release. Build and sign a release APK separately before distributing it publicly. The Android toolchain and deployed backend are prerequisites; this repository does not include a generated APK.

## Notes

- Cobra MemeScope is an educational memecoin research and tracking tool, not an exchange, broker, or custodian. It does not accept deposits, buy or sell crypto, or hold user funds. Connecting a wallet can show its SOL balance and detected token holdings; any optional wallet transaction, such as a donation, must be initiated and approved by the user.
- Market prices are informational and can be delayed. This app is not financial advice.
- Market Tape ranks newly profiled pools created within the last 30 days using observed price movement, volume, activity, and liquidity. DexScreener profile listings are not proof of organic virality or a definitive meme-token classification; a listing may be promoted.
- `GET /api/market/trending` merges recent profiles and latest/top boosted listings with per-chain GeckoTerminal new-pool discovery for Solana, Ethereum, Base, BNB Chain, Arbitrum, Sui, Polygon, and Avalanche. It returns up to 50 candidates, balancing discovery across chains and scanning additional candidates to replace explicit high-risk reviews when possible. Pools below $5,000 liquidity, below $1,000 24h volume, or at/below -20% 24h movement are excluded; the feed refreshes every 60 seconds and tags boosted listings. The list can contain fewer than 50 tokens when providers do not return enough qualifying pools. Sui market activity is screened, but its contract checks are marked unverified because the current risk providers do not support Sui. A review without detected issues is not a guarantee of safety. Feed candidates stay in the market list and are added to the browser's watchlist only when the user clicks the star; removing a token from the watchlist does not affect its market-feed visibility. A one-time browser migration clears legacy auto-tracked entries so only explicitly selected launches remain.
- Selecting a tracked launch opens its live market details, including selectable 1m, 5m, 1h, 2h, 3h, 5h, 8h, 1d, and 1mo candle intervals; candlestick or line chart styles; zoom/pan through available history; a list of up to eight discovered DEX pools; and the holder count when RugCheck (Solana) or GoPlus (supported EVM networks) reports one. The displayed market price refreshes every 15 seconds while details are open and briefly flashes green or red when the value changes. Holder counts are provider-reported snapshots; unavailable counts are shown as not reported rather than estimated. The month view groups daily candles by calendar month.
- The interface uses a consistent dark theme.
- On Android, users can install Cobra MemeScope as a progressive web app (PWA) from Chrome using the landing-page install section or Chrome's "Install app" menu. This is a web app, not a downloadable APK or a Play Store listing. Production installation requires HTTPS; localhost is allowed for development. The PWA shell does not make live market or API data available offline. A Capacitor Android wrapper is available in `frontend/android`; generating an APK still requires a deployed API endpoint and Android build/signing tools.
- Each launch gets separate contract-risk checks. Fast growth is not safety; the "Review Clear" filter only includes reviews with no reported flags or missing checks at scan time.
- Contract scans accept Solana mint addresses and EVM contract addresses. Solana checks use RugCheck; supported EVM checks use GoPlus; market liquidity, volume, and pair age use DexScreener. Provider outages or unsupported chains appear as unknown, not as clean results.
- The scanner highlights reported mint/freeze controls, developer share where available, holder concentration, honeypot/tax signals, liquidity, pool age, and observed buy/sell activity. A scan is not an audit and cannot guarantee a token is safe from a rug pull.
- To serve AdSense ads, add an approved publisher client ID and ad slot to `frontend/.env` as `VITE_ADSENSE_CLIENT` and `VITE_ADSENSE_SLOT`. This reserves and renders the ad placement; approval, traffic, and advertiser demand determine whether it earns revenue.
- Donations are native SOL on Solana and native gas tokens on configured EVM chains only. The app prepares a Solana transfer and asks Phantom to sign and send it; EVM wallets submit a native transfer transaction. EVM chains remain disabled until `VITE_DONATION_EVM_ADDRESS` contains the separate `0x…` recipient; the Solana destination cannot receive EVM assets. Every transfer requires wallet approval and is irreversible once confirmed.
- Sign-in supports email/password accounts and crypto wallets. Phantom, Solflare, and Backpack are supported on Solana; Coinbase Wallet, MetaMask, Rabby, Trust Wallet, Brave Wallet, and EIP-6963-discovered wallets are supported on EVM networks, including Base. New email accounts require a unique username, email, and a 10–128 character password. Wallet sign-in verifies a one-time signed message and never authorizes a transaction. Profile avatars are generated locally from a saved per-account seed.
- Phantom on Android Chrome opens the deployed site inside Phantom's in-app browser when no injected provider is available, then uses Phantom's injected Solana provider for connection and message signing. Other mobile platforms can connect through the encrypted HTTPS universal link. For Android builds, set both `VITE_API_URL` and `VITE_PUBLIC_APP_URL` in `frontend/.env.android` to the deployed public HTTPS origins before `npm run android:sync`; the APK registers the Phantom return link and must be rebuilt after this configuration. Desktop browser extensions continue to use the injected Phantom provider.
- The donor dashboard and `/api/admin/donors` are restricted server-side to the developer wallet configured in the application. Activity scans the latest 100 confirmed wallet transactions, counts inbound SOL transfers in a 30-day window, and does not include SPL tokens or prove transfer intent.
- The developer wallet can publish the global seasonal background from the private admin portal. The selected theme is stored in PostgreSQL and public clients refresh it automatically; run the backend schema migration after updating to add the `site_settings` and `landing_event_images` tables.
- Admins and staff can choose a JPEG, PNG, WebP, or GIF event photo from their device. Event images are stored in PostgreSQL and served publicly; uploads are limited to 5 MB.
- The authenticated wallet balance endpoint reports native SOL. `SOLANA_RPC_URL` can point to a dedicated Solana mainnet RPC provider; the public mainnet RPC is used by default. Sign-in challenges are stored in process memory and expire after five minutes.
- Email auth uses bcrypt-hashed passwords; email and wallet sessions use signed bearer tokens. Use HTTPS and a managed secrets store before deploying publicly.
- Set `FRONTEND_ORIGIN` to the comma-separated allowed frontend origins and provide a strong `JWT_SECRET` in production.
